# bc250-nucleos-arch: ядро 7 BC-250 в Arch / CachyOS (Limine)

**Языки:** [Português](arch-cachyos.md) · [English](arch-cachyos.en.md) · **Русский**

Версия `bc250-nucleos.sh` для **Arch/CachyOS с загрузчиком Limine**. Исходный скрипт работает только в Fedora/Nobara (GRUB с BLS).

Также устанавливает **ACPI-исправление от e-tho** (P-states/C-states, те же таблицы, что и «ACPI-исправление» BC250 Control Center) для каждой загрузки, **с дополнительным ядром и без него**, не заменяя Limine на GRUB/systemd-boot.

> Вопросы и сообщения скрипта на португальском.

> **Состояние на 2026-10-05:** скрипт написан и проверен **офлайн** (синтаксис, вспомогательные модули, правка копии реального `limine.conf`, таблица, созданная из реальной MADT платы, initramfs, собранный с хуком `acpi_override`, моделирование просмотра initrd так, как это делает ядро). **Проверено на плате 2026-10-05:** шаг 1 (`acpi`) и шаг 2 (`testar`, 14 потоков + 5 мин нагрузки) OK. См. [журнал проверок на плате](#журнал-проверок-на-плате).

## Плата

| | |
|---|---|
| Система | CachyOS (`linux-cachyos-deckify` 7.2.9), Limine 12.9.0, EFI, Secure Boot выключен, lockdown `none` |
| BIOS | P3.00 (12/09/2021), с заводской SSDT «AMD CPU» |
| Маска SMU | `0x77`: **скрыты ядра 3 и 7**; 12 потоков (APIC 0–5 и 8–13) |
| Предыдущие проверки (в Nobara) | **ядро 7 исправно**, ядро 3 дефектное |
| Цель | включить только ядро 7: **14 потоков** (APIC 0–5 и 8–15; APIC 6/7 = ядро 3 в простое) |

## Перед началом (обязательно)

1. **Выключите разгон CPU** и перезагрузитесь обычным образом:
   ```
   sudo systemctl disable bc250-smu-oc
   sudo reboot
   ```
   Разгон (3850 МГц, scale −31) был откалиброван на 6 ядрах. На исходной плате старый разгон с 7 ядрами приводил к зависанию изображения. Применённый разгон остаётся в SMU и **переживает тёплый сброс**. Скрипт отказывается работать, если `bc250-smu-oc` включён или запускался в текущей загрузке.
   Если разгон применён из приложения BC250 Control Center (а не службой), скрипт этого не обнаружит. Поэтому **не применяйте разгон из приложения** перед проверкой.
2. Работайте на ядре по умолчанию из пункта Limine (не в снимке и не на только что установленном ядре без перезагрузки).
3. SMT включён (подсчёт потоков предполагает 2 на ядро).

## Использование

```
cd ~/Downloads/bc250-7-core-unlock
sudo ./bc250-nucleos-arch.sh testar     # включает ядро 7 только на ОДНУ загрузку
sudo ./bc250-nucleos-arch.sh status     # результат; nproc должен показать 14
sudo ./bc250-nucleos-arch.sh instalar   # оставляет включённым по умолчанию (каждая холодная загрузка = 2 загрузки)
sudo ./bc250-nucleos-arch.sh desfazer   # убирает дополнительное ядро (ACPI-исправление не трогает)
sudo ./bc250-nucleos-arch.sh acpi           # ACPI-исправление e-tho при каждой загрузке
sudo ./bc250-nucleos-arch.sh acpi-desfazer  # убирает ACPI-исправление
```
Запускайте в отдельном терминале, потому что скрипт задаёт вопросы. `NUCLEOS="7"` по умолчанию; другой список можно передать через эту переменную.

Необязательная нагрузка во время тестовой загрузки: `sudo pacman -S stress-ng`, затем `stress-ng --cpu 14 --verify -t 10m`.

### `testar` (только одна загрузка)
1. Проверяет дистрибутив, Limine с one-shot, EFI, `CONFIG_ACPI_TABLE_UPGRADE`, плату, выключенный разгон, маску и MADT.
2. Создаёт cpio с новой MADT (+ SSDT от e-tho, если ACPI-исправления ещё нет в initramfs) и копирует его в `/boot/bc250-nucleos.cpio`.
3. Добавляет пункт `/bc250-nucleos` в конец `/boot/limine.conf`. Делает резервную копию `/boot/limine.conf.bc250-bak` (только в первый раз). В строку ядра добавляются `bc250.nucleos=teste` и `systemd.mask=` для служб разгона и governor.
4. Останавливает governor GPU, записывает `0xFF` в маску через SMU, выполняет `bootctl set-oneshot bc250-nucleos` и делает **тёплую** перезагрузку.
5. В тестовой загрузке служба `bc250-nucleos-teste.service` проверяет потоки, **удаляет пункт и cpio**, возвращает холодную перезагрузку и отключает себя. Следующая обычная перезагрузка возвращает заводское состояние.

### `instalar` (по умолчанию)
Можно запускать в обычной загрузке (12 потоков) или **сразу после успешного `testar`, ещё в тестовой загрузке**. Во втором случае используются заводская маска, базовое число потоков и исходная MADT, которые `testar` сохранил в `/var/lib/bc250-nucleos/` (только если в строке ядра есть `bc250.nucleos=teste` и результат `OK`).

Устанавливает `bc250-nucleos-boot.service`. При каждой холодной загрузке 1-я загрузка (обычный пункт, 12 потоков) записывает `0xFF` и делает тёплую перезагрузку в пункт `bc250-nucleos`. 2-я загрузка поднимается с 14 потоками. Пункт Limine пересоздаётся при каждой загрузке из пункта ядра, поэтому переживает `limine-entry-tool` и обновления.

Отключить на одну загрузку: в Limine клавиша `e` и добавить `bc250.nucleos.nao`. Отключить совсем: `sudo touch /etc/bc250-nucleos.desligado`. Если попытка не дала 14 потоков, новые попытки прекращаются (`sudo rm /var/lib/bc250-nucleos/falhou`, чтобы попробовать снова).

### `acpi` (ACPI-исправление при каждой загрузке)
Почему не установщик Control Center: он принимает только GRUB или systemd-boot Type #1 и считает Limine «UKI» (ошибочно: здесь `ENABLE_UKI=no`, и Limine загружает `vmlinuz` и `initramfs` по отдельности). Эта команда делает то же самое родным для Arch способом:

1. Проверяет дистрибутив, Limine, `limine-mkinitcpio`, хук `acpi_override`, `CONFIG_ACPI_TABLE_UPGRADE`, lockdown, BC-250 с BIOS P3.00 и **sha256** трёх SSDT (совпадают с e-tho v1.1.0 и с пакетом Control Center).
2. Отказывается, если уже есть другое исправление: загружены SSDT `PSTATES`/`STUBS`/`P_CST3` или `AMD CPU` rev ≥ 2, есть `bc250-acpi` в `limine.conf` или файлы `.aml` в `/etc/initcpio/acpi_override` или `/usr/lib/initcpio/acpi_override`.
3. Копирует SSDT в `/etc/initcpio/acpi_override/` и создаёт `/etc/mkinitcpio.conf.d/20-bc250-acpi.conf` с `HOOKS+=(acpi_override)`. Основной `mkinitcpio.conf` не редактируется.
4. Запускает `limine-mkinitcpio` и проверяет, что SSDT попали в ранний cpio initramfs пункта ядра. Если нет, сам всё откатывает.

Поскольку это drop-in для mkinitcpio, он переживает обновления ядра. Старые снимки Limine остаются без исправления (они используют старые initramfs).

После `acpi` проверка Control Center показывает «таблицы изменены другим исправлением» и блокирует его установщик. **Так и должно быть**, это предотвращает двойную установку.

### Дополнительное ядро + ACPI-исправление вместе
Пункт Limine `bc250-nucleos` загружает `bc250-nucleos.cpio` **перед** обычным initramfs. Чтобы SSDT никогда не загружались дважды, скрипт создаёт два cpio и при каждой загрузке выбирает один:

| ACPI-исправление установлено? | `bc250-nucleos.cpio` содержит | Результат при загрузке с дополнительным ядром |
|---|---|---|
| да (SSDT в initramfs) | `madt.cpio`: только MADT | новая MADT + SSDT один раз |
| нет | `final.cpio`: MADT + SSDT | новая MADT + SSDT один раз |

Выбор (`cpio_certo`) смотрит на ранний cpio initramfs, на который ссылается пункт ядра. Поэтому установка или удаление ACPI-исправления после дополнительного ядра не требует ничего переустанавливать.

## Если что-то пошло не так
- **Зависло:** выключите и включите плату. Холодная загрузка возвращает заводскую маску (`0x77`, 12 потоков).
- **Загрузилось с 16 потоками** (ядро 3 включено): служба сразу отключает CPU 6 и 7 и записывает это в `status`. Перезагрузитесь обычным образом.
- **Тестовая загрузка попала на обычный пункт:** вероятно, ID `bc250-nucleos` в Limine другой (см. ниже). Сохраните вывод `status` и `bootctl list`.
- **Limine не загружается:** выберите другой пункт в меню или восстановите `/boot/limine.conf.bc250-bak`.

### Исправление в проверке MADT
Исходная проверка требовала **UID = APIC+1** и отклонила бы эту BIOS. BIOS P3.00 нумерует UID последовательно только по активным ядрам (APIC 8 → UID 7). SSDT от e-tho используют `P000`…`P00F`, где `_CSD` группирует два потока на физическое ядро (P00E/P00F = ядро 7 = APIC 14/15), то есть P00x = APIC x. Согласованной является сгенерированная MADT (UID = APIC+1). Теперь проверка принимает и последовательную структуру. Любая другая структура по-прежнему отклоняется.

Сгенерированная таблица (проверена, контрольная сумма OK):
```
APIC 0-5   включены   (ядра 0-2)
APIC 6-7   ВЫКЛЮЧЕНЫ  (ядро 3, дефект)
APIC 8-15  включены   (ядра 4-7)
```

## Совместимость с BC250 Control Center

| Компонент | Влияние |
|---|---|
| Разгон CPU (`bc250-smu-oc`) | **Сначала выключить.** Перед повторным включением перекалибровать на 7 ядрах (автоопределение Control Center) |
| Cyan Skillfish Governor | OK: скрипт останавливает его перед обращением к SMU (запускает снова, если запись не удалась) и маскирует в тестовой загрузке |
| «Управление питанием CPU · ACPI» | **Не устанавливать из Control Center** (он не принимает Limine). Используйте `acpi` из этого скрипта: ставит те же таблицы и сочетается с дополнительным ядром без двойной загрузки |
| Ядро MastaG / другое ядро | Проверьте в нём `zcat /proc/config.gz \| grep ACPI_TABLE_UPGRADE`; не меняйте ядро посреди проверки |
| Mesa / GFX1013 / FSR4 | Не влияет |
| Mitigations | Не влияет |
| Отключение SMT | **Мешает** (подсчёт потоков перестаёт быть верным) |
| Управление вентилятором | Не влияет (лучше оставить включённым) |

## Защита от ядра 3 (аудит от 2026-10-05)

SMU принимает только «освободить все» (`0xFF`): после записи ядро 3 включено аппаратно до холодного сброса. Что не даёт ядру Linux его использовать:

| Уровень | Как | Проверено |
|---|---|---|
| Новая MADT | APIC 6 и 7 с `flags=0` (ни enabled, ни *online capable*) | `madt.cpio` в `/boot` идентичен сгенерированному; контрольная сумма OK; `possible=present=online=0-13`, в sysfs нет `cpu14/15`: их нельзя включить даже через hotplug |
| Пункт `bc250-nucleos` | отмечается (one-shot) только после записи пункта и проверки ядра (`uname -r`) | ID подтверждён в ходе проверки |
| Перезагрузка после загрузки с 14 потоками | **исправлено:** `_boot` теперь делает перезагрузку **холодной** (`acpi`/`cold`) и при успешной загрузке. Раньше оставалось значение ядра по умолчанию; тёплый сброс с `0xFF`, попавший на обычный пункт, поднял бы 16 потоков | |
| Обычный пункт с 16 потоками (проскочивший тёплый сброс) | служба сразу отключает потоки ядра 3 и продолжает | **исправлено:** раньше отключались `cpu6`/`cpu7` по **логическому номеру**. Ядро Linux нумерует CPU в порядке MADT: в этой загрузке `cpu6`/`cpu7` = APIC 8/9 (ядро 4, исправное). Теперь отключение идёт по **APIC ID** из `/proc/cpuinfo`, а неудача записывается в журнал |
| Попытка, не давшая 14 | файл `falhou`: новые попытки прекращаются, перезагрузка снова холодная | |

Оставшееся ограничение: если тёплый сброс попадёт на обычный пункт, ядро Linux разбудит ядро 3 во время загрузки, раньше, чем служба его отключит. Два исправления выше делают этот путь гораздо менее вероятным.

## Исправленная ошибка: `remember_last_entry` в Limine (2026-10-05)

При холодной загрузке в 22:03 плата поднялась с **12 потоками**, а служба записала `OK: 14 threads`. Две причины:
1. Limine (`remember_last_entry: yes`) хранит последний пункт в `LimineLastBootedEntry` (EFI). Там был `bc250-nucleos`, поэтому холодная загрузка сразу пошла на пункт с новой MADT, но с заводской маской: ядро Linux ~20 с ждало отсутствующие APIC 14/15 (`Total of 12 processors activated` на 20,2 с).
2. `threads()` использовала `nproc --all`, которая считает **объявленные** CPU (14 в новой MADT), а не **активные** (12).

Исправление: `threads()` считает активные CPU (`/proc/cpuinfo`), а `_boot` стирает `LimineLastBootedEntry`, если там `bc250-nucleos`. Следующая холодная загрузка возвращается на `default_entry`; one-shot эту переменную не использует. Это была «неподтверждённая точка» про `remember_last_entry` ниже: предположение, что служба пойдёт по обычному пути, оказалось неверным из-за подсчёта.

## Разгон CPU с ACPI-исправлением (детектор Control Center)

С ACPI-исправлением частотой управляет Linux (`acpi-cpufreq` + `schedutil`). Под нагрузкой детектора `schedutil` оставляет часть ядер в более низких P-states (1577–2184 МГц). `bc250-detect` считает это троттлингом и **прерывается на первом шаге** (остаётся на `3500 + цель % 100`, например 3550 / scale −2), при любом VID.

Измерено 2026-10-05 (частота 8 ядер из SMU, нагрузка на 14 потоков): с `performance` все на 3550, кроме ядра 3 (дефектное, без нагрузки, 1577 МГц: детектор правильно считает его неактивным); со `schedutil` ядра колеблются между 1577 и 2184.

**Чтобы определить разгон:** регулятор `performance` на время определения, потом вернуть прежний:
```
echo performance | sudo tee /sys/devices/system/cpu/cpufreq/policy*/scaling_governor
# автоопределение в Control Center
echo schedutil | sudo tee /sys/devices/system/cpu/cpufreq/policy*/scaling_governor
```
(при следующей загрузке регулятор и так вернётся к `schedutil`).

## Планировщик `scx_lavd` (CachyOS) и частота

CachyOS использует планировщик sched_ext `scx_lavd`. В режиме **Auto** (`--autopilot`) он уплотняет ядра и задаёт целевую частоту, которой следует `schedutil`: в `stress-ng` на 14 потоков при **загрузке 99% на всех CPU** 6 из них остались на **1707 МГц** (измерено 2026-10-05 с разгоном 3850/−31). Вероятно, это и причина прерывания автоопределения разгона (раздел выше).

Решение: режим **Gaming** (`--performance`) по умолчанию в `/etc/scx_loader.toml` (`default_mode = "Gaming"`, резервная копия в `.bak`; действует после `systemctl restart scx_loader` или при следующей загрузке). Результат: все 14 CPU на 3842 МГц под нагрузкой, а в простое то же потребление, что и в Auto (PPT ~31,7 Вт, ядра на 800 МГц, C3 ~97% времени).

Нагрузка с разгоном 3850/−31 + 7 ядер + Gaming: 14/14 passed, 0 failed (остановлено на ~6,5 мин, ~4,5 мин все на 3850), Tctl стабильно 68 °C, PPT ~62–66 Вт, 1175–1181 мВ.

## Ядро
Для работы ядру нужен `CONFIG_ACPI_TABLE_UPGRADE=y`, и оно не должно быть в режиме lockdown (Secure Boot). Иначе оно игнорирует новую MADT. После тёплого сброса BIOS показывает все 8 ядер, и **дефектное ядро 3 запустилось бы**. Скрипт проверяет оба условия, а если всё же поднялось 16 потоков, отключает CPU 6 и 7.

## Неподтверждённые моменты
- ~~ID пункта в Limine~~: **подтверждено** 2026-10-05: `bootctl set-oneshot bc250-nucleos` загрузил пункт `/bc250-nucleos`.
- `remember_last_entry: yes` в `limine.conf`: в режиме `testar` не важно, потому что пункт удаляется. В режиме `instalar`, если Limine запомнит пункт `bc250-nucleos`, холодная загрузка попадёт на него с заводской маской. Ядро Linux попытается разбудить отсутствующие APIC 14/15 (задержка в несколько секунд), поднимется с 12 потоками, и служба пойдёт по обычному пути.
- Limine объединяет несколько `module_path` в один initrd; cpio с ACPI идёт первым и без сжатия, как требует ядро. Ядро (`lib/earlycpio.c`) последовательно проходит несжатые cpio, пока не дойдёт до сжатой части. Моделирование с собранным initramfs: `apic.aml SSDT-CPU SSDT-PST SSDT-STUBS AuthenticAMD.bin`, каждый по одному разу.
- Таблицы e-tho с **заводской MADT** (последовательные UID) в обычном пункте: тот же сценарий, в котором Control Center и e-tho устанавливают их на заводских платах, но на этой плате ещё не наблюдался.

Каждый шаг в отдельном терминале (скрипт задаёт вопросы). Сохраняйте вывод `status` на каждом этапе.

**Шаг 1: только ACPI-исправление (12 потоков)**
```
sudo ./bc250-nucleos-arch.sh acpi

cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_driver      # сравнить с тем, что было (acpi-cpufreq / amd-pstate)
cat /sys/devices/system/cpu/cpu0/cpuidle/state*/name
```
Если зависло или появилась ошибка ACPI: выберите в Limine снимок (без исправления) и выполните `sudo ./bc250-nucleos-arch.sh acpi-desfazer`.

**Шаг 2: ядро 7 на одну загрузку (14 потоков)**
```
sudo ./bc250-nucleos-arch.sh testar      # должно появиться "a correcao ACPI ja esta na initramfs; o cpio leva so a MADT"
# сам делает тёплую перезагрузку

```
Если зависло: выключите и включите плату (холодная загрузка = заводское состояние).

**Шаг 3: сделать постоянным**
```
sudo ./bc250-nucleos-arch.sh instalar
```
Затем перекалибруйте разгон CPU на 7 ядрах, прежде чем снова включать `bc250-smu-oc`.

## Журнал использования (`registro/bc250-registro.py`)

Служба `bc250-registro.service` (устанавливается в `/usr/local/lib/bc250-registro/`) запускается при каждой загрузке и **каждые 60 с** пишет строку в `~/Desktop/bc250-registro/ГГГГ-ММ-ДД.csv` (один файл в день, владелец — ваш пользователь, ~150 байт на строку ≈ 200 КБ/день):

`data_hora, tctl_c, gpu_c, ppt_w, cpu_mv, n0..n7 (МГц каждого физического ядра из SMU; n3 = дефектное ядро, всегда низкая частота), threads_online, carga_1min, scx_modo, mce_boot`

(`data_hora` = дата и время, `carga_1min` = нагрузка за 1 минуту, `scx_modo` = режим планировщика.)

Читает SMU через `bc250_smu` из Control Center с `flock` (не мешает governor GPU). Остановить: `sudo systemctl disable --now bc250-registro`.
